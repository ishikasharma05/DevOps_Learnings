# web-service — Helm Chart

A Helm chart that deploys a configurable, scalable nginx web service to a Kubernetes cluster. Built as a hands-on exercise in Helm templating fundamentals — configurable values, context scoping, and label conventions.

## What this chart does

Deploys an nginx Deployment with:

- Configurable image repository and tag (defaults to `nginx:latest`)
- Configurable replica count (defaults to `3`)
- Consistent `app.kubernetes.io/name` labeling across the Deployment metadata, pod selector, and pod template

## Chart structure

```
web-service/
├── Chart.yaml
├── values.yaml
└── templates/
    ├── deployment.yaml
    ├── _helpers.tpl
    └── NOTES.txt
```

Non-essential scaffold files generated by `helm create` (Service, Ingress, HPA, ServiceAccount, HTTPRoute, and the default test suite) were removed, since this chart's scope is limited to the Deployment.

## values.yaml

```yaml
replicaCount: 3
image:
  repository: nginx
  tag: latest
```

## Key template logic

`templates/deployment.yaml` demonstrates two Helm templating concepts worth calling out:

**1. Scoping into a sub-map with `with`**

```yaml
{{- with .Values.image }}
image: "{{ .repository }}:{{ .tag }}"
{{- end }}
```

Inside a `{{- with .Values.image }}` block, the dot context (`.`) switches to point at `.Values.image` instead of the chart's root context. That's why `.repository` and `.tag` work directly, with no `.Values.image.` prefix needed.

**2. The context-switch gotcha**

Because `with` reassigns `.`, anything from the root context — like `.Values.replicaCount` — becomes unreachable *inside* that block. The fix is to capture it into a variable *before* entering the block:

```yaml
{{- $replicaCount := .Values.replicaCount -}}
...
spec:
  replicas: {{ $replicaCount }}
```

The same pattern is used for the chart name:

```yaml
{{- $name := .Chart.Name -}}
```

so it stays accessible for labeling regardless of scope changes elsewhere in the template.

## Environment used

- Standalone EC2 instance (Ubuntu), kept separate from the local machine to avoid installing Helm/kubectl locally
- [`kind`](https://kind.sigs.k8s.io/) (Kubernetes in Docker) as the target cluster — a free, local alternative to a managed cluster like EKS, sufficient for validating chart logic without incurring cloud costs

## Usage

**Install with defaults:**
```bash
helm install web-service .
```

**Override values at install time:**
```bash
helm install web-service . --set replicaCount=5 --set image.tag=1.27
```

**Verify:**
```bash
kubectl get pods -l app.kubernetes.io/name=web-service
```

**Validate templates without installing:**
```bash
helm lint .
helm template web-service .
```

## Why Helm

Kubernetes on its own requires managing raw YAML files per environment, with no built-in versioning, rollback, or templating. Helm addresses this as a package manager for Kubernetes:

- **Templating** — one chart, many configurations, driven by `values.yaml` or `--set` overrides
- **Release management** — `helm upgrade` / `helm rollback` track deployment history
- **Packaging & reuse** — charts bundle everything an app needs into one shareable, installable unit
