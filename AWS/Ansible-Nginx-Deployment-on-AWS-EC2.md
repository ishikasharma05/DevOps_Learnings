# Ansible Nginx Deployment on AWS EC2

A hands-on Ansible project demonstrating **Galaxy roles, playbooks, inventories, handlers, variables, Jinja2 templates, and Ansible Vault**, built on an AWS EC2 Ubuntu instance.

The EC2 instance currently acts as both the **Ansible control node** and the **managed node** (via `localhost`), as a first step before scaling to a multi-instance setup.

---

## 1. Overview

This project automates the installation and configuration of Nginx using Ansible, covering:

- AWS EC2 instance provisioning, security groups, and SSH key access
- Ansible installation and role scaffolding via `ansible-galaxy`
- Inventory and playbook structure
- Task, handler, variable, and template organization inside a role
- Idempotent configuration management
- Secrets management with Ansible Vault

---

## 2. Architecture

```text
Windows PC (ssh -i key.pem)
        │
        ▼ SSH
AWS EC2 — Ubuntu instance
        │
        ▼ Ansible
     localhost (managed node)
        │
        ▼
      Nginx
```

**Current setup:** controller and managed node are the same EC2 instance (`localhost ansible_connection=local`), used to learn Ansible fundamentals without provisioning multiple instances.

**Planned next step:** split into a dedicated controller EC2 instance managing a separate web-server EC2 instance over SSH — this is where Ansible's real multi-node value shows up.

## 3. Environment

| Component | Detail |
|---|---|
| Instance name | `ansible-controller` |
| AMI | Ubuntu Server LTS |
| Architecture | 64-bit |
| Key pair | `.pem` file, kept local — never committed |
| Security group | SSH (22) restricted to your IP; HTTP (80) opened only if you need browser access to Nginx |
| Access | SSH via `ssh -i <key>.pem ubuntu@<public-ip>` from Windows |

**Public IP** is found under *EC2 → Instances → your instance → Public IPv4 address*. It's assigned on start and — unless you attach an Elastic IP — changes if the instance stops/starts, so don't hardcode it anywhere committed.

### What's Galaxy scaffold vs. what you wrote

Running `ansible-galaxy init webserver-deployment` generates the **entire `webserver-deployment/` folder** below as an empty skeleton — every subfolder shown above is created automatically, not hand-built:

```bash
ansible-galaxy init webserver-deployment
```

| Auto-generated by Galaxy (empty until you fill them) | You edited/populated these |
|---|---|
| `README.md`, `defaults/main.yml`, `files/`, `handlers/main.yml`, `meta/main.yml`, `tasks/main.yml`, `templates/`, `tests/`, `vars/main.yml` | Content inside `tasks/main.yml`, `nginx-install.yml`, `nginx-configuration.yml`, `handlers/main.yml`, `defaults/main.yml`, `templates/nginx.conf.j2`, `files/nginx.conf` |

The top-level files (`inventory`, `webserver.yml`, `group_vars/`, `vault/`) are **not** part of the Galaxy scaffold — you create those yourself at the project root, outside the role. This structure is identical to the GCP version of this project — only the underlying VM provider and connection method (`.pem` + public IP vs. `gcloud compute ssh`) differ.

## 5. What Each Folder Is For (and whether you need it)

| Folder/file | Purpose | Required to run this playbook? |
|---|---|---|
| `tasks/` | The actual steps Ansible executes (install, configure). This is the heart of the role. | **Required** |
| `handlers/` | Actions triggered only when a task reports a change (e.g. restart Nginx after a config edit). | Required if any task uses `notify` |
| `defaults/` | Role-level default variables, lowest precedence — meant to be overridden. | Optional, but good practice over hardcoding |
| `vars/` | Role-level variables, higher precedence than `defaults/`. Use for values you don't expect callers to override. | Optional |
| `files/` | Static files copied as-is to the managed node (no templating). | Only if a task uses `copy` with a static file |
| `templates/` | Jinja2 templates (`.j2`) rendered with variables before being placed on the managed node. | Only if a task uses `template` |
| `meta/` | Role metadata — dependencies on other roles, author info, supported platforms. Mostly relevant if publishing to Galaxy or depending on other roles. | Not required for a local/private project |
| `tests/` | A minimal inventory + playbook Galaxy scaffolds for testing the role in isolation. | Not required; safe to delete if unused |
| `README.md` (inside the role) | Documents the role itself — its variables, dependencies, example usage. | Not required to run, but expected in any role meant to be reused |
| `group_vars/` (project root) | Variables applied to a whole inventory group (e.g. all hosts, or `[local]`). | Optional — only needed once you have more than one host or environment |
| `vault/` | Where encrypted secrets live. | Only required if the role needs secrets (DB passwords, API keys, etc.) |

**Bare minimum to keep Ansible running:** `inventory`, `webserver.yml`, and inside the role — `tasks/main.yml` plus whatever `files/` or `templates/` those tasks reference. Everything else (`meta/`, `tests/`, `vars/`, role `README.md`) can be trimmed if you don't need it — Galaxy generates them by default, but Ansible doesn't require them to execute.

## 6. How to Update the Main Files

- **Add or change a step Nginx should perform** → edit `tasks/nginx-install.yml` or `tasks/nginx-configuration.yml`, then re-import it from `tasks/main.yml` if it's a new file.
- **Change what triggers a restart** → edit the `notify:` line in the relevant task, and the actual restart logic in `handlers/main.yml`.
- **Change a config value (port, path, etc.)** → don't hardcode it in `tasks/` or `templates/` — set it in `defaults/main.yml` (or `group_vars/all.yml` if it should apply project-wide) and reference it as `{{ variable_name }}`.
- **Change the actual Nginx config content** → edit `templates/nginx.conf.j2` if it needs variables, or `files/nginx.conf` if it's static.
- **Add a new host or environment** → add it to `inventory`, and put environment-specific variables in `group_vars/`.
- **Add or rotate a secret** → edit via `ansible-vault edit vault/credentials.yml`, never hand-edit the encrypted file directly.

## 7. File Contents

Since this repo doesn't split code into a browsable file tree separately from this README, here's the actual content of every file, in the order you'd create them.

### `inventory`

```ini
[local]
localhost ansible_connection=local
```

### `webserver.yml` (project root — the playbook)

```yaml
---
- hosts: localhost
  become: true

  roles:
    - webserver-deployment
```

### `group_vars/all.yml`

```yaml
nginx_port: 80
backend_port: 8080
app_root: /var/www/myapp
```

### `vault/credentials.yml` (before encrypting)

```yaml
db_username: db
db_password: db_pass
```

Encrypt it before it ever touches Git:

```bash
ansible-vault encrypt vault/credentials.yml
```

---

### `webserver-deployment/defaults/main.yml`

```yaml
nginx_port: 80
backend_port: 8080
```

### `webserver-deployment/files/nginx.conf`

Static Nginx config file, copied as-is to the managed node by `nginx-configuration.yml` below. Content depends on what you actually want Nginx serving — put your real server block here.

### `webserver-deployment/handlers/main.yml`

```yaml
---
- name: Restart nginx
  ansible.builtin.service:
    name: nginx
    state: restarted
```

### `webserver-deployment/tasks/main.yml`

```yaml
---
- name: Install Nginx
  ansible.builtin.import_tasks: nginx-install.yml

- name: Configure Nginx
  ansible.builtin.import_tasks: nginx-configuration.yml
```

### `webserver-deployment/tasks/nginx-install.yml`

```yaml
---
- name: Install Nginx
  ansible.builtin.apt:
    name: nginx
    state: present
    update_cache: true
```

### `webserver-deployment/tasks/nginx-configuration.yml`

```yaml
---
- name: Copy Nginx configuration
  ansible.builtin.copy:
    src: nginx.conf
    dest: /tmp/nginx.conf
    owner: root
    group: root
    mode: '0644'
  notify:
    - Restart nginx
```

> Note: this copies to `/tmp`, not a live Nginx config path — see **Known Limitations** below. It's kept exactly as originally written rather than "fixed" here, so this README matches what the role actually does today.

### `webserver-deployment/templates/nginx.conf.j2`

```nginx
server {
    listen {{ nginx_port }};

    location / {
        proxy_pass http://localhost:{{ backend_port }};
    }
}
```

This is a starting template — swap in your real server block. The point is that `{{ nginx_port }}` and `{{ backend_port }}` are pulled from `defaults/main.yml` or `group_vars/all.yml` instead of being hardcoded.

## 8. Concepts Demonstrated

| Concept | Where it lives |
|---|---|
| Inventory | `inventory` — defines managed hosts |
| Playbook | `webserver.yml` — entry point, calls the role |
| Role | `webserver-deployment/` — reusable automation unit |
| Tasks | `tasks/main.yml` imports `nginx-install.yml` and `nginx-configuration.yml` |
| Handlers | `handlers/main.yml` — restarts Nginx only when config changes |
| Variables | `defaults/main.yml`, `group_vars/all.yml` |
| Templates | `templates/nginx.conf.j2` — Jinja2-driven config |
| Static files | `files/nginx.conf` |
| Secrets | `vault/credentials.yml`, encrypted with Ansible Vault |
| Idempotency | Verified by re-running the playbook and confirming `ok` instead of `changed` |

```bash

```

### Accessing Nginx from a browser (optional)

Only if you've opened port 80 in the security group:

```text
http://YOUR_EC2_PUBLIC_IP
```

Don't open port 80 unless you actually need public HTTP access — every open port is attack surface.

## 11. Secrets Management

Sensitive variables (e.g. `vault/credentials.yml`) are encrypted with Ansible Vault and never committed in plaintext.

```bash
ansible-vault encrypt vault/credentials.yml
ansible-vault view vault/credentials.yml
ansible-vault edit vault/credentials.yml
```

**Never committed to this repo:**
- The `.pem` private key
- AWS access keys / secret access keys
- Vault passwords
- Unencrypted database passwords
- API keys or other credentials

## 12. Known Limitations (current state)

- Controller and managed node are the same EC2 instance — doesn't yet exercise Ansible's real remote-orchestration strength.
- `nginx-configuration.yml` copies config to `/tmp` rather than the live Nginx config directory, so there's no `nginx -t` validation gate before reload in this version.
- Single-host inventory only; no host groups, no environment separation (dev/staging/prod).
- Public IP is not static — no Elastic IP attached, so it changes on instance restart.

## 14. Security Notes

- Restrict SSH (22) to your IP, not `0.0.0.0/0`.
- Never upload the `.pem` file to GitHub or store it inside the project repo.
- Don't commit AWS access/secret keys — use IAM roles where possible instead of long-lived keys.
- Keep the Ansible Vault password outside the repository.
- Stop or terminate unused EC2 instances, and remove unused EBS volumes/Elastic IPs, to avoid unnecessary AWS charges.
